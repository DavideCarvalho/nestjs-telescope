Every option below is passed to `TelescopeModule.forRoot({ … })`. All are optional — the defaults give you a zero-config SQLite store, request/exception capture, and overload protection; in production you also protect the routes (see [Protecting the routes](#protecting-the-routes)). This page is the consolidated reference; each option links out to the concept or recipe that covers it in depth.

## Capture & correlation

| Option | Default | Description |
|---|---|---|
| `enabled` | `true` | Master switch. Compute inline (e.g. `NODE_ENV !== 'production'`). |
| `watchers` | `[]` | Built-in + custom watchers (queries, jobs, mail, cache, …). Request and exception capture wire automatically. See [Capture](/docs/concepts/capture). |
| `extensions` | `[]` | Installable extensions (`TelescopeExtension[]`) that bundle watchers, a navigable entry type, dashboard pages, and server-side data providers. Additive — extension watchers merge into `watchers`. See [Extensions](/docs/concepts/extensions). |
| `sampling` | _none_ | Per-type keep-fractions for high-volume streams (e.g. `{ cache: 0.1 }`). |
| `redact` | sensible defaults | Deep-redaction of `headers` / `query` / `body` paths plus content bounds (`maxDepth`, `maxStringLength`, …). See [Performance](/docs/concepts/performance#memory-bounds). |
| `resolveUser` | reads `request.user` | Resolves the authenticated user recorded on a request entry. |
| `exceptions` | `{ captureHttp4xx: false }` | How thrown exceptions become entries. By default 4xx control flow is **not** recorded as an exception. See [Exception capture](/docs/concepts/capture#exception-capture). |
| `exceptions.processCrashes` | _off_ | Opt-in capture of `unhandledRejection` / `uncaughtException` as `exception` entries. Attaching these listeners changes whether your process dies, so read the exit contract before enabling. See [Process-level crashes](/docs/concepts/capture#process-level-crashes--exceptionsprocesscrashes). |
| `requestCapture` | 128 KiB cap + binary content-types skipped | Gates a request body **before** `record()` sees it — `maxBodyBytes`, `skipBodyContentTypes`, `skipBody(request)`. See [Request body capture gate](/docs/concepts/capture#request-body-capture-gate--requestcapture). |
| `registerRequestMiddleware` | `true` | Auto-register request-capture middleware. Set `false` when using `setGlobalPrefix(...)` and register capture in bootstrap instead — also exclude Telescope's own routes with `telescopeMountPaths()` (`app.setGlobalPrefix('api', { exclude: telescopeMountPaths() })`), or the dashboard/API/assets get shifted under the prefix too. See [Request context for your routes](/docs/recipes/request-context#capture-under-a-global-prefix--telescoperequestcapture). |

## Storage & retention

| Option | Default | Description |
|---|---|---|
| `storage` | embedded SQLite | A `StorageProvider`. Swap for Redis / MikroORM / in-memory. See [Storage](/docs/concepts/storage). |
| `prune` | _none_ | Retention window driving the scheduled pruner (e.g. `{ after: '24h' }`); `perType` for [per-type cutoffs](/docs/concepts/storage#per-type-retention). |
| `archive` | _none_ | Export a type's entries to a sink **before** the pruner deletes them. See [Archiving before prune](/docs/concepts/storage#archiving-before-prune). |
| `prune.batchSize` | `1000` | Rows per bounded `DELETE`. A lock-duration knob — see [Bounded batched deletes](/docs/concepts/storage#bounded-batched-deletes). |
| `prune.maxBatchesPerCycle` | `50` | Hard ceiling on batches per scope per cycle, so a backlog cannot turn one tick into an hour-long loop. |
| `prune.batchPauseMs` | `50` | Pause between batches. Only paid when a second batch is needed, so a healthy store never waits. |
| `prune.lock` | storage lease | Cross-process prune lock, so a fleet prunes once per cycle rather than once per pod. `false` to opt out, or your own `TelescopePruneLock`. See [Pruning once per fleet](/docs/concepts/storage#pruning-once-per-fleet-not-once-per-pod). |
| `prune.lockTtlMs` | `max(intervalMs * 3, 60s)` | Lease TTL — how long the fleet may go unpruned after a holder is killed mid-cycle. |

## Protecting the routes

| Option | Default | Description |
|---|---|---|
| `decorators` | none | Class decorators applied to the console controllers the module mounts (API, live stream, MCP), e.g. `[UseGuards(AuthenticationGuard), Can(ConsolePolicy, 'view')]`. **Required in production** unless `routes: false`: with `NODE_ENV=production` and no `decorators` (an empty array counts as none) the boot fails. Each mounted controller is also marked `Can.Anyone()`-open; a `Can()` passed here is still enforced. Static top-level option on `forRootAsync`. Pass the same list to `TelescopeUiModule.forRoot`. See [Protecting the routes](/docs/dashboard/auth). |
| `routes` | `true` | `false` mounts no controller; every provider keeps running and the module exports what the controllers need, so your own subclasses of `TelescopeController` / `StreamController` / … serve the routes with your decorators. Always boots. Keep `path` set to the mount. Static top-level option on `forRootAsync`. |
| `imports` | `[]` | Extra Nest `imports` merged into the module, for whatever your `decorators` need. |
| `mutations` | `false` | Turns on the console's mutations: queue actions, **Prune now**, [request replay](/docs/dashboard#replay-a-request), on-demand profiling. Off: they answer `403`. Who may call them is decided by your `decorators`. |
| `clientErrors` | `{ enabled: false }` | Public frontend error ingestion. Public by design: it takes no `decorators` and is outside the production rule. See [Reporting frontend errors](/docs/recipes/reporting-frontend-errors). |

### Other modules

| Option | Default | Description |
|---|---|---|
| `TelescopeUiModule.forRoot({ decorators })` | none | Class decorators on the dashboard page controller. **Required in production** unless `routes: false`, like `TelescopeModule`'s. |
| `TelescopeUiModule.forRoot({ routes })` | `true` | `false` mounts no controller; extend `TelescopeUiController` yourself. |
| `TelescopeOtelMetricsModule.forExporter(exporter, { decorators })` | none | Class decorators on the `GET /metrics` controller, applied whenever given. **Not required in production** by default: Prometheus usually scrapes unauthenticated inside the cluster. `/metrics` exposes your metrics, so keep it reachable only by the scraper (network policy, or `decorators`). |
| `TelescopeOtelMetricsModule.forExporter(exporter, { requireProtectionInProduction })` | `false` | `true` puts `/metrics` under the production rule: with `NODE_ENV=production` and no `decorators` the boot fails. Ignored with `routes: false`. |
| `TelescopeOtelMetricsModule.forExporter(exporter, { routes })` | `true` | `false` mounts no controller and exports the exporter under `TELESCOPE_OTEL_EXPORTER`; extend `TelescopeOtelMetricsController` yourself. |

## Health, alerts & AI

| Option | Default | Description |
|---|---|---|
| `pulse` | _none_ | Health-snapshot tuning; `slowRouteMs` (default `1000`) is the p99 a route must reach to count as a slow-request hotspot. |
| `alerts` | _none_ | Pluggable-channel alerting (Slack / webhook / custom) + rules. See [Alerts](/docs/dashboard#alerts). |
| `ai` | _none_ | AI exception diagnosis. See [AI diagnosis](/docs/packages/ai). |
| `aiMetrics` | `{ prometheus: false }` | `prometheus: true` serves the AI-usage and agent-run metrics at `GET <path>/api/metrics` (Prometheus text), behind the API gate. See [AI usage and agent runs](/docs/dashboard/ai). |
| `profiling` | `{ enabled: false }` | On-demand V8 CPU flamegraphs — strictly opt-in. `enabled`, `sampleRate`, `maxConcurrent`, `minDurationMs`, `samplingIntervalMicros`. See below and [CPU profiling](/docs/concepts/profiling). |
| `traceContext` / `traceLink` | _none_ | OpenTelemetry trace stamping + deep-link template. See [`-otel`](/docs/packages/otel). |
| `explainQuery` | _none_ | Host hook that runs an engine `EXPLAIN` for a captured query. See [Explain slow queries](/docs/dashboard#explain-slow-queries). |

## Queues & schedules

| Option | Default | Description |
|---|---|---|
| `queueManagers` | `[]` | Live queue managers (BullMQ / SQS). A `watchers` entry that structurally implements the `QueueManager` SPI (`driver`, `init`, `listQueues`, `counts`, `listJobs`, `getJob`) is **auto-registered** — this array is only needed for standalone managers that aren't also watchers. See [queue managers](/docs/packages/queue-managers). |
| `scheduleManagers` | `[]` | Schedule managers (`@nestjs/schedule`). Same auto-registration: a `watchers` entry implementing the `ScheduleManager` SPI (`listTasks`) — e.g. `ScheduleWatcher` — is picked up automatically; listing it in both arrays is safe (deduped by identity, inited once). See [the schedule watcher](/docs/packages/watchers). |

## Agents & resilience

| Option | Default | Description |
|---|---|---|
| `mcp` | disabled | MCP server for coding agents. `true` enables it; omitted/`false` answers 404. Protected by your `decorators` like every console route. See [MCP server](/docs/concepts/mcp). |
| `overloadProtection` | `true` (200ms) | Pause capture under event-loop pressure. See below. |

### `overloadProtection`

```ts
overloadProtection?: boolean | { maxEventLoopLagMs?: number; startupGraceMs?: number };
```

Telescope samples the process event-loop delay (`perf_hooks.monitorEventLoopDelay`) on a 1s interval and, when the **p99 lag** crosses the threshold, **pauses the Recorder** (`record()` becomes a no-op) until the lag recovers — so a telescope under load can never amplify an incident.

- `true` (the **default**) — protect with a **200ms** p99 threshold.
- `false` — disable.
- `{ maxEventLoopLagMs }` — tune the threshold (defaults to 200 when omitted).
- `{ startupGraceMs }` — grace window (default **~5000ms**) after the guard arms during which it samples but never pauses or logs, so the synchronous bootstrap stall (DI wiring, migrations, codegen blocking the loop) can't trip the guard on a transient. Set `0` to arm immediately; ignored when protection is off.

```ts
TelescopeModule.forRoot({
  overloadProtection: { maxEventLoopLagMs: 100, startupGraceMs: 0 }, // pause sooner, arm at once
});
```

<Callout type="info">
  The sampling timer is `unref`'d (it never keeps the host's loop alive), and the guard degrades to a no-op when `perf_hooks.monitorEventLoopDelay` is unavailable. See [Performance → Overload protection](/docs/concepts/performance#overload-protection--pause-under-event-loop-pressure).
</Callout>

### `profiling`

```ts
profiling?: {
  enabled?: boolean;                // default false — master switch
  sampleRate?: number;              // default 0 — fraction (0–1) auto-captured
  maxConcurrent?: number;           // default 1 — max simultaneous captures
  minDurationMs?: number;           // default 0 — discard captures shorter than this
  samplingIntervalMicros?: number;  // default 1000 — V8 sampling interval
};
```

On-demand V8 CPU flamegraph profiling. **Strictly opt-in and OFF by default** — while disabled no profiler is constructed, `node:inspector` is never loaded, and the request path is untouched beyond one boolean check. Enable it for manual "profile the next N requests" captures (via the `POST /api/profiles/arm` endpoint / the dashboard's **Profiles** tab), and/or set `sampleRate` to auto-capture a uniform fraction of traffic.

```ts
TelescopeModule.forRoot({
  profiling: { enabled: true, sampleRate: 0.01, minDurationMs: 50 },
});
```

<Callout type="info">
  Captures are aggregated into a bounded `cpu_profile` entry (a flame tree, not the raw `.cpuprofile`) that inherits the profiled request's batch/trace context. Arming is a **mutation**, so it needs `mutations: true`. See [CPU profiling](/docs/concepts/profiling).
</Callout>
