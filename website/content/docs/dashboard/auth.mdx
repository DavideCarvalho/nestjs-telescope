Telescope ships no access control of its own. Its routes are ordinary Nest routes, protected with NestJS's first-party tools, [`@nestjs/authentication`](https://www.npmjs.com/package/@nestjs/authentication) and [`@nestjs/authorization`](https://www.npmjs.com/package/@nestjs/authorization). There are two ways, and one rule for production.

## Protecting the routes

### 1. `decorators` on the mounted controllers

Keep the routes Telescope mounts and hand it the class decorators to put on them, the same shape as `@nestjs/mcp`'s `decorators` option:

```ts
import { AuthenticationGuard } from '@nestjs/authentication';
import { AuthorizationModule, Can, Policy } from '@nestjs/authorization';
import { Module, UseGuards } from '@nestjs/common';
import { TelescopeModule } from '@dudousxd/nestjs-telescope';
import { TelescopeUiModule } from '@dudousxd/nestjs-telescope-ui';

@Policy()
export class ConsolePolicy {
  view(user: User | null) {
    return user?.roles.includes('admin') === true;
  }
}

const protect = [UseGuards(AuthenticationGuard), Can(ConsolePolicy, 'view')];

@Module({
  imports: [
    AuthorizationModule.forRoot(),
    TelescopeModule.forRoot({ decorators: protect }),
    TelescopeUiModule.forRoot({ decorators: protect }),
  ],
  providers: [ConsolePolicy],
})
export class AppModule {}
```

A guest gets 401, a user the policy denies gets 403, and an admin gets the console. With `forRootAsync`, `decorators` is a static top-level option next to `path` (the routes are built before any factory runs). Each registration gets fresh controller subclasses, so decorators never leak between registrations.

| Module | Controllers `decorators` covers |
|---|---|
| `TelescopeModule.forRoot({ decorators })` | `TelescopeController` (API), `StreamController` (live feed), `TelescopeMcpController` (MCP) |
| `TelescopeUiModule.forRoot({ decorators })` | `TelescopeUiController` (the page and its assets) |
| `TelescopeOtelMetricsModule.forExporter(exporter, { decorators })` | `TelescopeOtelMetricsController` (`GET /metrics`) |

<Callout type="info">
  The dashboard page is a full-page navigation: the browser sends your app's cookies, not an `Authorization` header. The authentication strategy in front of `TelescopeUiModule` must read a cookie session. The MCP endpoint is the opposite: agent clients send a header, so use a Bearer-capable strategy there.
</Callout>

### 2. Mount the routes yourself (`routes: false`)

`TelescopeModule.forRoot({ routes: false })`, `TelescopeUiModule.forRoot({ routes: false })` and `TelescopeOtelMetricsModule.forExporter(exporter, { routes: false })` mount no controller. Every provider keeps running: request capture, watchers, storage, pruning, alerts and the services. The modules export what the controllers need, so a subclass of an exported controller resolves in your own module:

```ts
import { AuthenticationGuard } from '@nestjs/authentication';
import { AuthorizationModule, Can } from '@nestjs/authorization';
import { Controller, Module, UseGuards } from '@nestjs/common';
import {
  StreamController,
  TelescopeController,
  TelescopeModule,
} from '@dudousxd/nestjs-telescope';
import { TelescopeUiController, TelescopeUiModule } from '@dudousxd/nestjs-telescope-ui';

@Controller('ops/telescope/api')
@UseGuards(AuthenticationGuard)
@Can(ConsolePolicy, 'view')
class ConsoleApi extends TelescopeController {}

@Controller('ops/telescope/api')
@UseGuards(AuthenticationGuard)
@Can(ConsolePolicy, 'view')
class ConsoleStream extends StreamController {}

@Controller('ops/telescope')
@UseGuards(AuthenticationGuard)
@Can(ConsolePolicy, 'view')
class ConsolePage extends TelescopeUiController {}

@Module({
  imports: [
    AuthorizationModule.forRoot(),
    // `path` is still where the console lives: the request-capture self-skip
    // and the page's asset URLs use it.
    TelescopeModule.forRoot({ path: 'ops/telescope', routes: false }),
    TelescopeUiModule.forRoot({ path: 'ops/telescope', routes: false }),
  ],
  controllers: [ConsoleApi, ConsoleStream, ConsolePage],
  providers: [ConsolePolicy],
})
export class OpsModule {}
```

The base classes carry no guard of their own, so your decorators are the whole gate. Mount only what you use:

| Controller to extend | Mount at | Serves |
|---|---|---|
| `TelescopeController` | `<path>/api` | the API the dashboard reads |
| `StreamController` | `<path>/api` | the live SSE feed (`/stream`) |
| `ClientErrorController` | `<path>/api/client-errors` | front-end error ingestion, only if `clientErrors` is enabled |
| `TelescopeMcpController` | `<path>/api/mcp` | the MCP endpoint, only if `mcp` is enabled |
| `TelescopeUiController` (`-ui`) | `<path>` | the dashboard page and its assets |
| `TelescopeOtelMetricsController` (`-otel`) | anywhere | `GET metrics` (or call `exporter.prometheus()` from your own handler) |

List `ClientErrorController` and `TelescopeMcpController` before `TelescopeController` when you mount them, as `TelescopeModule` does. With `forRootAsync`, `routes` is a static top-level option next to `path`.

Why `routes: false` and not `path: false` like `@nestjs/mcp`: Telescope's `path` keeps a job when nothing is mounted (it tells request capture which URLs are the console's own, and rebases the page's asset URLs), so it stays a string and a separate `routes` flag turns the controllers off. The three modules use the same name.

## The production rule

With `NODE_ENV === 'production'`, `TelescopeModule` and `TelescopeUiModule` refuse to mount their routes with no `decorators` (an empty array counts as none). The boot fails at module build, before the app listens, with an error naming both ways:

```txt
TelescopeModule: refusing to mount unprotected routes with NODE_ENV=production. Protect them with the official NestJS tools (@nestjs/authentication, @nestjs/authorization), one of two ways:
  1. decorators on the mounted controllers: TelescopeModule.forRoot({ decorators: [UseGuards(AuthenticationGuard), Can(ConsolePolicy, 'view')] })
  2. mount the routes yourself: TelescopeModule.forRoot({ routes: false }) + @Controller('telescope/api') @Can(ConsolePolicy, 'view') class ConsoleApi extends TelescopeController {}
```

`routes: false` always boots: protecting the controllers you mount is your job. Outside production an undecorated console mounts open, so local work needs no setup.

Every controller Telescope mounts is also marked open to `@nestjs/authorization`'s deny-by-default global `AuthorizationGuard` (as `Can.Anyone()` would), so an undecorated dev console keeps answering once your app adopts that package. The mark only opens routes that declare no requirement: a `Can(...)` passed in `decorators` is still enforced.

### `GET /metrics` (otel): outside the rule by default

A Prometheus scrape usually runs unauthenticated inside the cluster, so `TelescopeOtelMetricsModule` mounts an undecorated `/metrics` in production too. It exposes your metrics (route and queue names, error counts, AI cost), so keep it reachable only by the scraper: a network policy that keeps it off your public ingress, or `decorators`, which apply to it in every environment whenever you pass them. To put it under the same rule as the console, opt in:

```ts
TelescopeOtelMetricsModule.forExporter(exporter, {
  requireProtectionInProduction: true, // default false
  decorators: [UseGuards(BearerGuard)],
});
```

With `requireProtectionInProduction: true` and no `decorators` (an empty array counts as none), the boot fails with the same error as the console's. `routes: false` still always boots.

## Public by design: the client-error beacon

`POST <path>/api/client-errors` takes error reports from any visitor's browser, signed in or not. It is off until `clientErrors.enabled` (404 while off). Because guests must reach it, `TelescopeModule` mounts it **without** your `decorators`, and it does not count toward the production rule. It keeps its own abuse dampers: a byte cap (`maxBodyBytes`) and a per-IP rate limit (`rateLimit`). To put it behind your own auth, use `routes: false` and extend `ClientErrorController` with your decorators.

## Mutations

Queue retry / remove / promote / retry-all / redrive / enqueue, **Prune now**, request replay and on-demand profiling are mutations. They are a feature switched on with `mutations: true`; while it is off they answer 403 and the dashboard hides their buttons (`meta.mutationsEnabled`). Who may call them is decided by your decorators, like every other route.

For a rule on mutations stricter than on reads, mount the routes yourself and override those methods with an extra requirement. `@nestjs/authorization` requires both the class's and the method's `Can(...)`. An override is a new function, so re-declare its route decorators:

```ts
@Controller('ops/telescope/api')
@UseGuards(AuthenticationGuard)
@Can(ConsolePolicy, 'view')
class ConsoleApi extends TelescopeController {
  @Post('retention/prune')
  @HttpCode(200)
  @Can(ConsolePolicy, 'operate')
  override prune() {
    return super.prune();
  }
}
```

## Migrating from the old options

| Old option | Now |
|---|---|
| `authorizer` | `decorators: [UseGuards(AuthenticationGuard), Can(ConsolePolicy, 'view')]`, or `routes: false` + your controllers |
| `guards: [MyGuard]` (core and UI) | `decorators: [UseGuards(MyGuard)]` on both modules |
| `dashboardAuth` (login / session modes, `unauthenticatedPage`, the session cookie, `/api/auth/*`) | your app's own sign-in through `@nestjs/authentication`; the page authenticates from your app's cookie |
| `openTelescopeConsole`, `useOpenTelescopeConsole`, `<OpenTelescopeConsoleButton>`, `./react/console` | a plain link: `telescopeConsoleUrl(basePath)` from `@dudousxd/nestjs-telescope-ui/client` |
| `authorizeAction` | `mutations: true`; a stricter rule via an overriding method with its own `@Can(...)` |
| `clientErrors.authorize` | `routes: false` + your own `ClientErrorController` subclass |
| `mcp: { token }` | `mcp: true` + a Bearer strategy in `decorators` |
| the built-in "open in dev, closed in production" gate | the production rule above |
